1What exactly should the model learn?

1.1 One task, several possible objectives

Use the customer-support task from slide 3. Let $X$ contain the instruction and message, and let $Y$ be the desired response:

Instruction: Extract issue and product. Return JSON.
Message: My headphones won’t charge even after being plugged in overnight.
Response: {"issue": "charging_failure", "product": "headphones"}

Training should improve $p_\theta(Y\mid X)$. The response teaches both a semantic decision and an output format. A model can emit valid JSON with the wrong issue, or select the right issue in invalid JSON. Keep those failure modes separate when evaluating.

$$\mathcal L_{\mathrm{token}}=-\frac{1}{M}\sum_i\sum_{t=1}^{|Y_i|}\log p_\theta(y_{i,t}\mid X_i,y_{i,<t}),\qquad M=\sum_i |Y_i|.$$

Here $Y_i$ includes the response’s stopping token. This token-mean objective gives longer responses more total weight. Averaging each example’s mean loss instead gives equal weight to examples; either is a choice, but they are not the same objective. With accumulation, normalize over the intended scored-token count, as in Handout #16.

1.2 Work through the boundary by hand

For a tiny illustration, pretend the response has just two tokens, y1 y2. These are symbolic tokens, not the actual tokenization of the JSON above. In a decoder-only model, the output at position $j$ predicts the token at $j+1$.

Two masks, two jobsCausal attention masking prevents a position from seeing future tokens. Loss masking chooses which next-token predictions contribute to training. Ignoring a prompt target does not hide that prompt from the response or prevent gradients from flowing through its representations. Gold response prefixes are visible during teacher-forced training; generated prefixes are used at inference.

In a real implementation, apply the model’s chat template consistently during training and generation, then inspect the tokenized prompt/response boundary. Tokenizing two strings separately and concatenating them need not match tokenizing the combined string. Some causal-LM APIs shift labels internally: follow their contract and do not shift a second time. Reject or repair examples with zero scored response tokens after truncation.

2Freeze parameters, not the gradient path

2.1 When a frozen backbone needs no backward pass

For head tuning, compute $H=f_{\mathrm{frozen}}(X)$ and logits $Z=HW_{\mathrm{head}}^\top$. If neither the backbone parameters nor its inputs require gradients, $H$ has no autograd history. Training the head needs $H$ but not the backbone’s internal activations.

requires_grad_(False) controls parameter gradients. eval() controls behavior such as dropout; it does not freeze weights. Choose dropout behavior deliberately and configure the optimizer after selecting trainable parameters. See the PyTorch autograd notes.

# Sketch: backbone and head are separate modules, with no shared parameters.
backbone.requires_grad_(False)
head.requires_grad_(True)
optimizer = torch.optim.AdamW(head.parameters(), lr=1e-4)
with torch.no_grad():
    h = backbone(input_ids)
logits = head(h)  # Keep this OUTSIDE no_grad().

If an input embedding and the vocabulary head share the same Parameter, changing its trainability affects both uses. Check parameter identity before claiming that only the output mapping changes. Here we assume separate parameters; untying them can itself require an additional copy of the weights.

A limitation that a larger head cannot fixIf two messages have identical frozen features, $f(X_1)=f(X_2)$, every shared output head gives them the same next-token distribution for the same response prefix. Yet “won’t charge” and “won’t pair” require different issue labels. Enlarging or training the head cannot recover a distinction already lost in its inputs. An adapter before that information is lost may preserve it; an adapter placed only after the collision cannot. This is a capacity argument, not a guarantee that LoRA learns the right distinction. Work through a numerical example in Exercise 6A.

2.2 A frozen layer can transmit gradients

Now put a trainable adapter before a frozen linear layer: $h=Wx$, where $W$ is frozen but $x$ depends on the adapter. Given upstream gradient $g=\partial\mathcal L/\partial h$, we still need

$$\frac{\partial\mathcal L}{\partial x}=W^\top g.$$

We can skip storing/calculating the parameter gradient $\partial\mathcal L/\partial W$, but cannot skip the derivative with respect to $x$. A no_grad() block around this layer cuts that connection. The same problem occurs if you detach the activations between adapters.

Head tuning

Frozen backbone → trainable head → loss

Backward stops after the head. Retain its input features.

Adapters across layers

Early adapter → frozen layer → late adapter → loss

Backward crosses the frozen layer to reach the early adapter.

2A · A silent implementation bug

In a network with early and late adapters, someone wraps the frozen layer between them in no_grad(). Loss still decreases. Does that prove both adapters are learning? What would you inspect?

Predict, then reveal

No. The late adapter can learn while the early adapter is disconnected. After backward, inspect every intended trainable parameter’s .grad, then compare weights before and after an optimizer step. A missing gradient differs from a zero gradient: the early factor A can legitimately have a zero first-step gradient under standard LoRA initialization (§3). The lab reproduces this exact bug.

3A small update with a precise budget

3.1 Count the update, not the base matrix

For $W_0\in\mathbb R^{d_{\mathrm{out}}\times d_{\mathrm{in}}}$, LoRA uses

$$h=W_0x+sB(Ax),\quad A\in\mathbb R^{r\times d_{\mathrm{in}}},\quad B\in\mathbb R^{d_{\mathrm{out}}\times r},\quad s=\alpha/r.$$

The trainable update has $r(d_{\mathrm{in}}+d_{\mathrm{out}})$ parameters and rank at most $r$. The base matrix remains stored and frozen. It need not be low rank: the constraint is on the update. During training, compute $A x$ then $B(Ax)$ without materializing the dense product $BA$. This is the formulation in Hu et al., LoRA.

3.2 Why initialize only one factor to zero?

Standard LoRA initializes $A$ randomly and $B=0$, so the adapter initially contributes zero. For one input and upstream gradient $g$,

$$\nabla_B\mathcal L=s\,g(Ax)^\top,\qquad \nabla_A\mathcal L=s\,B^\top g x^\top.$$

Initially, the task gradient for $A$ is zero, but the gradient for $B$ can be nonzero. After $B$ changes, $A$ can receive a task gradient. If both factors start at zero, both task gradients are zero. This is a bilinear dead start, not a reason to initialize the entire adapter randomly and lose the base-model starting behavior.

3C · Do the first update by hand

Use scalars $x=1$, $W_0=1$, $A=2$, $B=0$, $s=1$, and $\mathcal L=\tfrac{1}{2}(h-3)^2$, where $h=W_0x+BAx$. With SGD learning rate 0.1 and no decay, find both factor gradients and the new output.

Predict, then reveal

Initially $h=1$, so $g=-2$. Then $\nabla_B=-4$ and $\nabla_A=0$. The simultaneous update gives $B=0.4$, $A=2$, and new $h=1.8$. Starting with both factors zero would leave both unchanged. Weight decay is excluded here; it can change a nonzero factor even when its task gradient is zero.

3.3 Rank and placement buy different things

A higher rank expands the possible update at each targeted projection. More target projections let updates enter at more points in the computation. At fixed adapter count, these choices compete: Q/V at rank 16 and Q/K/V/O at rank 8 cost the same under square-projection assumptions. Equal parameter budgets do not imply equal learned functions or runtime. Compare them on validation data.

Scaling $s$ matters too. Changing rank with fixed $\alpha$ also changes $\alpha/r$. Record rank, target modules, scaling convention, dropout, and learning rate together. Prefer the smallest configuration meeting the task requirement rather than assuming the largest fitting rank must generalize best.

4Budget training memory and computation separately

4.1 Fewer trainable parameters is only part of the story

Use four accounts: model weights, gradients, optimizer state, and activations retained for backward. Add temporary buffers and implementation overhead when measuring a real run. Low-rank adapters reduce parameter-related memory compared with full tuning; they do not remove the dense base weights or all activation storage.

MethodParameter gradients / Adam stateBackward activations
Full tuningAll trainable model parametersNeeded through the model
Head tuningHead onlyRetain head inputs; no internal frozen-backbone history under §2 assumptions
LoRAAdapter parameters only, unless other parameters are explicitly trainedBackward traverses layers between adapters and the loss

Increasing micro-batch size or sequence length can make activation memory dominate. Checkpointing trades recomputation for less activation storage. Gradient accumulation changes the effective batch without requiring all micro-batch graphs to remain live. Therefore a smaller adapter checkpoint does not establish a smaller peak training allocation.

4.3 What a frozen matrix still computes

For $n$ token rows and a dense $d\times d$ projection, using two FLOPs per multiply–add, the matrix products cost approximately:

ProductFull tuningFrozen base inside LoRA
Forward: $XW^\top$$2nd^2$$2nd^2$
Input gradient: $GW$$2nd^2$ when needed$2nd^2$ when needed to reach earlier adapters
Weight gradient: $G^\top X$$2nd^2$Skipped for frozen $W$

The LoRA branch adds approximately $4ndr$ forward FLOPs for a square matrix, plus its backward work. Thus freezing the dense base can save weight-gradient computation, while retaining its forward and input-gradient work. This isolated projection is not an end-to-end Transformer speed model: attention, activations, optimizer work, checkpointing, and kernels also matter. Measure tokens/second and validation quality at a stated budget.

Training and deployment use different computationsDuring training use $W_0x+sB(Ax)$. For one deployed adapter, merge $W_{\mathrm{merged}}=W_0+sBA$ once, then use the original dense projection shape. That removes the extra adapter branch but does not turn the base model into a smaller dense model. The original paper’s method section distinguishes the training branch and inference merge.

6Core practice: diagnose before scaling up

6A · Can a head recover a lost distinction?

Two toy input vectors are $x_1=(1,1)^\top$ and $x_2=(1,-1)^\top$, but they need different labels. The frozen backbone projects them with $W_0=[1\;0]$. Calculate both features. Can any head that sees only those features distinguish the inputs? Now apply the rank-one update $\Delta W=[0\;1]$ to that projection. Calculate the new features and give a separating threshold.

Predict, then reveal

Both original features equal 1, so any head depending only on that scalar produces identical outputs. The adapted projection is $[1\;1]$, giving features 2 and 0. A threshold at 1 separates them. This update changes the representation where the distinguishing second coordinate is still available. Putting an adapter after the original scalar projection cannot recover that discarded coordinate. A rank-one update can therefore make a distinction that head tuning cannot, even with a much larger head.

6B · Is a merged adapter a compressed model?Adapted from Spring 2025 Quiz 3, Q3.1.5

You merge a rank-8 adapter into $W_0$ for deployment. Must the dense projection now use fewer inference FLOPs? What changes if adapters remain separate?

Predict, then reveal

No. The merged matrix has the same dimensions as $W_0$, so its dense projection has the same arithmetic shape. Separate adapters add the small low-rank branch but permit sharing the unchanged base among tasks. Merging saves branch overhead, not the base projection.

6C · Three bugs in one setup
model.eval()                         # “freeze the base”
optimizer = AdamW(model.parameters())
# Insert trainable adapters here, AFTER creating the optimizer.
with torch.no_grad():
    logits = model(input_ids)
loss = cross_entropy(logits, targets)
loss.backward()

Identify three independent reasons this is not a valid adapter-training setup.

Predict, then reveal

eval() does not freeze base weights. Adapters inserted after optimizer construction are absent from its parameter groups. Wrapping the whole forward in no_grad() removes the loss’s gradient path, so backward cannot train those adapters. Insert adapters, set and audit trainability, then build the optimizer over intended trainable parameters; keep the required graph enabled. Separately follow the model’s target-shifting and loss-mask contract.

6D · Why did the adapter checkpoint fail elsewhere?

An adapter checkpoint loads into a model with compatible tensor shapes, but outputs are wrong. Name three pieces of metadata you would check beyond the rank.

Predict, then reveal

Check the exact base checkpoint revision, tokenizer/chat template and vocabulary, targeted module names, adapter scaling convention, and any separately trained modules such as a head. Shape compatibility alone does not imply functional compatibility. Save this metadata alongside the adapter and verify a fresh-load output against a fixed input.

The lab’s original teaching module is short enough to inspect completely:

class LoRALinear(nn.Module):
    """Teaching implementation; optional existing base, no adapter dropout/auto-merge."""
    def __init__(self, din, dout, r=2, alpha=8, *, base=None):
        super().__init__()
        if r <= 0:
            raise ValueError("rank must be positive")
        self.base = nn.Linear(din, dout, bias=False) if base is None else base
        self.base.requires_grad_(False)
        weight = self.base.weight
        self.A = nn.Parameter(torch.randn(r, din, device=weight.device,
                                         dtype=weight.dtype) * 0.1)
        self.B = nn.Parameter(weight.new_zeros(dout, r))
        self.scale = alpha / r

    @classmethod
    def from_linear(cls, base, r=2, alpha=8):
        # Reuse the exact layer, including its bias, dtype, device, and weights.
        return cls(base.in_features, base.out_features, r, alpha, base=base)

    def forward(self, x):
        return self.base(x) + self.scale * F.linear(F.linear(x, self.A), self.B)

To adapt an existing model, reuse its actual layer instead of constructing a fresh random base. For example, replacing a model’s projection can look like this:

model.requires_grad_(False)  # Freeze before injecting adapters.
original = model.proj  # An existing nn.Linear from the loaded model.
x = example_features  # Inputs to this projection, not raw token IDs.
with torch.no_grad():
    expected = original(x).clone()
model.proj = LoRALinear.from_linear(original, r=2, alpha=8)
torch.testing.assert_close(model.proj(x), expected, rtol=0, atol=0)
optimizer = torch.optim.AdamW(
    [p for p in model.parameters() if p.requires_grad], lr=1e-4)

This replacement retains the exact base weight, bias, dtype, and device, and freezes that layer’s base parameters. It does not freeze the rest of the model. For adapter-only training, freeze the full model before replacing the desired projections; then audit all trainable names before creating the optimizer. The lab’s check_existing_layer checks exact initial output parity, a nonzero adapter update, and unchanged base weights and bias.

The nested F.linear calls apply A and then B. PyTorch stores linear weights as [out_features, in_features]; the math uses column vectors while the implementation accepts batches of row vectors. The frozen base call remains outside no_grad() so the module works correctly when its input depends on an earlier adapter.
