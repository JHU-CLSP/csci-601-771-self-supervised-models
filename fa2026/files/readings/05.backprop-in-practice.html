1Backprop is the chain rule on a graph

Slides 111–136 · Computation graphs and local/upstream gradients

The slides' worked graph (123–134)

Let $a=x_1+x_2$, $b=ax_3$, and $f=b-x_4$, with $(x_1,x_2,x_3,x_4)=(5,4,3,2)$. Compute the forward values, then all four input derivatives in reverse order.

Answer

The forward values are $a=9$, $b=27$, and $f=25$. Seed $\partial f/\partial f=1$. Subtraction gives $\partial f/\partial b=1$ and $\partial f/\partial x_4=-1$. Multiplication gives $\partial f/\partial a=x_3=3$ and $\partial f/\partial x_3=a=9$. Addition sends the upstream value 3 to both $x_1$ and $x_2$. Thus $\nabla f=(3,3,9,-1)^\top$. Each local derivative multiplies the sensitivity arriving from its output.

There is no new mathematics in backpropagation. It is the chain rule from Handout #1 §1.3, applied to a composition of functions, organized so that nothing gets computed twice. The organizing idea is to stop thinking of a network as a formula and start thinking of it as a computation graph: one node per elementary operation, edges carrying values forward.

Take a concrete function and build its graph:

$$ f(x, y, z) = \ln x + e^{y}\cdot z $$

Forward pass: walk left to right, storing each intermediate value. Backward pass: walk right to left, and at every node apply the same rule —

The only rule you need $$\text{downstream} = \text{upstream} \times \text{local}$$ The upstream gradient is $\partial f / \partial(\text{this node's output})$, handed to you by the node ahead. The local gradient is the derivative of this node alone with respect to its input — something you can write down without knowing anything about the rest of the graph. Multiply, pass it back. That locality is the whole trick: each node needs to know only its own derivative.
Exercise 1.1 — propagate by hand Quiz 1, sp2023, Q2; also HW3, sp2025, §5

For $f(x,y,z) = \ln x + e^{y}\cdot z$ at $(x,y,z) = (1, 3, 2)$:

  1. Run the forward pass. Give $h_1$, $h_2$, $h_3$ and $f$.
  2. Give the local gradient at each node — $\partial h_1/\partial x$, $\partial h_2/\partial y$, $\partial h_3/\partial h_2$, $\partial h_3/\partial z$, $\partial f/\partial h_1$, $\partial f/\partial h_3$.
  3. Combine them to get $\partial f/\partial x$, $\partial f/\partial y$ and $\partial f/\partial z$.
Answers

1. Forward.

NodeExpressionValue at $(1,3,2)$
$h_1$$\ln x$$\ln 1 = 0$
$h_2$$e^{y}$$e^{3} \approx 20.086$
$h_3$$h_2 \cdot z$$2e^{3} \approx 40.171$
$f$$h_1 + h_3$$0 + 2e^{3} \approx 40.171$

2. Local gradients. Each depends only on its own node:

$$ \frac{\partial h_1}{\partial x} = \frac{1}{x} = 1, \qquad \frac{\partial h_2}{\partial y} = e^{y} = e^{3}, \qquad \frac{\partial h_3}{\partial h_2} = z = 2, \qquad \frac{\partial h_3}{\partial z} = h_2 = e^{3}, $$ $$ \frac{\partial f}{\partial h_1} = 1, \qquad \frac{\partial f}{\partial h_3} = 1 \qquad\text{(addition passes gradient through unchanged).} $$

Notice that $\partial h_3/\partial z$ needs $h_2$'s value — which is exactly why the forward pass stores its intermediates. A multiplication node hands each input the other input as its local gradient.

3. Combine, right to left.

$$ \frac{\partial f}{\partial x} = \underbrace{1}_{\partial f/\partial h_1}\cdot\underbrace{\frac{1}{x}}_{\text{local}} = \mathbf{1} $$ $$ \frac{\partial f}{\partial z} = \underbrace{1}_{\partial f/\partial h_3}\cdot\underbrace{h_2}_{\text{local}} = e^{3} \approx \mathbf{20.086} $$ $$ \frac{\partial f}{\partial y} = \underbrace{1}_{\partial f/\partial h_3}\cdot\underbrace{z}_{\partial h_3/\partial h_2} \cdot\underbrace{e^{y}}_{\partial h_2/\partial y} = 2e^{3} \approx \mathbf{40.171} $$

Check them against autograd — three lines, and worth actually running: 

x = torch.tensor([1.0], requires_grad=True)
y = torch.tensor([3.0], requires_grad=True)
z = torch.tensor([2.0], requires_grad=True)

f = torch.log(x) + torch.exp(y) * z
f.backward()
x.grad, y.grad, z.grad     # tensor([1.]), tensor([40.1711]), tensor([20.0855])

2Why backwards?

The chain rule does not tell you which direction to evaluate in. You could go left to right, computing $\partial(\text{everything})/\partial x$ as you sweep forward — that is forward-mode differentiation, and it is perfectly valid. So why does everyone go backwards?

Count the passes. For a function $f : \mathbb{R}^n \to \mathbb{R}^m$:

One pass gives you…Passes needed for the full Jacobian
Forward mode the derivative of everything with respect to one input $n$ — one per input
Reverse mode the derivative of one output with respect to everything $m$ — one per output

Now look at what we actually need. Training minimizes a scalar loss with respect to every parameter: $n$ is in the billions, $m = 1$. Reverse mode gets the whole gradient in one backward pass; forward mode would need billions of them. That asymmetry — and nothing else — is why backpropagation runs backwards.

A useful consequence The backward pass costs roughly the same as the forward pass — a small constant factor more, because each node does a couple of multiplications instead of one. So a training step costs about 2–3× an inference step, regardless of depth. Backprop is also linear in the number of layers, not quadratic: each node is visited once. (That "quadratic in the number of layers" claim is a perennial quiz distractor — see §5.)

The price is memory. Every intermediate value the backward pass will need must be kept from the forward pass — that is what $\partial h_3/\partial z = h_2$ was telling us in §1. Activation memory, not parameter memory, is what usually decides the largest batch you can fit, and techniques like gradient checkpointing exist purely to trade recomputation against it.

3What autograd actually does

PyTorch builds the graph from §1 for you, at runtime, as your forward code executes. There is no compilation step and no special syntax: ordinary Python arithmetic on tensors records itself. 

import torch

w = torch.tensor([2.0], requires_grad=True)     # a leaf we want gradients for
x = torch.tensor([3.0])                         # data: no requires_grad, no gradient

y = w * x                                       # y remembers: "I came from a mul"
loss = (y - 1.0) ** 2                           # ...and so on, node by node

print(y.grad_fn)        # <MulBackward0 ...>    -- the recorded operation
print(loss.requires_grad)   # True              -- inherited from w

loss.backward()         # walk the recorded graph, right to left
print(w.grad)           # tensor([30.]) -- d/dw (wx-1)^2 = 2(wx-1)x = 2(5)(3)
print(x.grad)           # None -- x never asked for gradients

Four things in there deserve emphasis.

  • requires_grad marks what you want gradients for. It propagates: any tensor computed from a requires_grad tensor also carries gradients. Model parameters have it set by default; your data does not, and should not.
  • grad_fn is the graph. Each non-leaf tensor holds a reference to the operation that produced it and to its inputs. "Building the graph" is not a separate phase — it is the forward pass.
  • .backward() consumes the graph. By default the graph is freed as it is traversed, which is why calling backward() twice on the same loss raises an error rather than silently doubling your gradient.
  • .grad accumulates. It is added to, never replaced — hence optimizer.zero_grad(), and Handout #1 Exercise 1.5c.
Turning it off, and why you must Recording the graph costs time and — mostly — memory. When you are not going to call backward(), say so: 
model.eval()
with torch.no_grad():                    # record nothing; free the memory
    val_loss = F.cross_entropy(model(x_val), y_val)

Forgetting no_grad around an evaluation loop is one of the most common out-of-memory causes there is: you are storing activations for the entire validation set in order to compute gradients you then throw away. tensor.detach() does the same job for a single tensor — it returns a copy cut out of the graph, which is what you want when logging a loss value or feeding a model's own output back in as data.

3.1  The loop, annotated

Handout #4 §1.4 introduced minibatch gradient descent. Here is its training loop, with every line now accounted for: 

for x_batch, y_batch in dataloader:
    optimizer.zero_grad()              # .grad accumulates -- clear last step's
    logits = model(x_batch)            # forward: compute AND record the graph
    loss = F.cross_entropy(logits, y_batch)     # one scalar -- reverse mode needs m = 1
    loss.backward()                    # traverse the graph, fill every .grad
    optimizer.step()                   # theta <- theta - lr * grad   (Handout #4 §1.3)

The order is forced. backward() needs the graph, so it must follow the forward pass; step() needs the gradients, so it must follow backward(); and zero_grad() must happen before backward() or you add this step's gradients to the last one's. Every model in the rest of this course trains with exactly these five lines.

Who computes, who updates, who clears? Adapted from Quiz 1, sp2024, Q1.14–16

After a forward pass has produced a scalar loss, explain the roles and valid ordering of loss.backward(), optimizer.step(), and optimizer.zero_grad(set_to_none=True). Does backward() change parameter values? Can clearing gradients at the end of a step also be correct?

Work it out, then reveal the answer

Clear old gradients, run the forward pass, call backward() to accumulate derivatives into leaf parameter .grad buffers, then call step() to update parameters. Backward alone does not update their values. Clearing after the update also works if gradients are clear before the first backward pass and none are unintentionally carried into the next one. Clearing between backward and step discards the gradients the optimizer needs.

Predict the accumulation Adapted from Quiz 1, sp2024, Q1.15–16 (coding extension)

import torch

Work it out, then reveal the answer

The outputs are 4, 7, and 3. The second backward adds its contribution 3 to the existing 4. Clearing removes the earlier contribution. The parameter remains 2 throughout because no optimizer update occurs.

What does nn.Module contribute? Adapted from Quiz 1, sp2024, Q1.21

Is nn.Module an optimizer, a data loader, or a base class for composing neural-network components? If a learned weight is stored as an ordinary tensor attribute, will model.parameters() automatically include it?

Work it out, then reveal the answer

It is the base class for neural-network components. Assigning an nn.Parameter registers a learned parameter; assigning a child module registers that component. An ordinary tensor attribute is not automatically a parameter, even if it has requires_grad=True. An optimizer built from model.parameters() will therefore miss that tensor.

4Reading real code: micrograd

Everything above is now in your head. The rest of your career it will be in someone else's repository, written by people who were not trying to teach you anything. Being able to open an unfamiliar file, find the four lines that matter, and recognize them as something you already understand is a skill in itself — and it is learnable. Each handout from here on ends with one short reading of real, widely used code.

The one for backprop is Karpathy's micrograd: a scalar-valued autograd engine in about 150 lines, plus a small neural-net library on top of it. It is a real, working reverse-mode autodiff implementation — the same algorithm PyTorch runs, with the tensors, the kernels, the device handling and the twenty years of performance work stripped away. What is left is §1–§3 of this handout, in Python you can read in one sitting.

Try it

Two files, both worth opening in a browser tab beside this page:

  • micrograd/nn.py — 60 lines. Neuron, Layer, MLP, and how a model exposes its parameters.

What to assess as you read. Not "do I understand every line" — you will, and that is not the point. The question is whether you can point at the place in the file where each idea from this handout lives: the computation graph, the local derivatives, gradient accumulation, the reverse topological traversal, and the parameter interface. The four subsections below walk those five, then §4.5 hands the file back to you.

4.1  The graph is built by the forward pass

There is no graph data structure anywhere in micrograd, and no function that constructs one. Every node builds itself, at the moment the operation that produced it is executed:

engine.py · Value.__init__

def __init__(self, data, _children=(), _op=''):
    self.data = data
    self.grad = 0
    # internal variables used for autograd graph construction
    self._backward = lambda: None
    self._prev = set(_children)
    self._op = _op # the op that produced this node, for graphviz / debugging / etc

That is the whole node: a number (data), a slot for its gradient (grad, initialized to zero and not to None — remember that), the set of nodes it was computed from (_prev), and a closure (_backward) that knows how to push a gradient one step further back. The default _backward is a no-op, which is exactly right for a leaf: an input has no children to send anything to.

_prev is the edge set of §1's diagram. It points backwards, from a node to its inputs, because backwards is the only direction the algorithm ever needs to walk. This is PyTorch's grad_fn from §3, in nine lines: _op is the string PyTorch would render as MulBackward0, and _backward is the function behind it.

4.2  Local derivatives, and why +=

Now the operations. Each one does two things: compute the output value, and install the closure that will later distribute the output's gradient to the inputs.

engine.py · Value.__mul__

def __mul__(self, other):
    other = other if isinstance(other, Value) else Value(other)
    out = Value(self.data * other.data, (self, other), '*')

    def _backward():
        self.grad += other.data * out.grad
        other.grad += self.data * out.grad
    out._backward = _backward

    return out

Read the two lines inside _backward against §1's rule. out.grad is the upstream gradient $\partial L/\partial \text{out}$; other.data is the local derivative $\partial \text{out}/\partial \text{self}$, which for a product is just the other operand. Their product is the downstream gradient. Downstream = upstream × local is not a slogan about backprop; it is line 1 of _backward, in every op in the file. Check the others and you will find nothing new — __add__ passes out.grad through unchanged (local derivative $1$), __pow__ multiplies by $n x^{n-1}$, and relu multiplies by (out.data > 0), a Python bool doing duty as the $\{0,1\}$ gate.

The += is the part to slow down on. It is gradient accumulation — §3's claim that .grad adds rather than overwrites, and the reason your training loop needs zero_grad(). Here you can see precisely why it must be a sum. Consider $y = x \cdot x + x$. The node x is reached along three separate edges, and each one delivers its own contribution: two from the product, one from the sum. The correct derivative $2x + 1$ only appears if they are added up.

Change one character

Replace both += with = and run x = Value(3.0); y = x*x + x; y.backward(). Correct is x.grad == 7.0. With the overwrite you get 3.0 — the last edge to be processed wins and the other two are erased. Note what this bug does not do: it does not crash, it does not produce a NaN, and on a graph where every node happens to have one consumer it gives the right answer. It just quietly trains a worse model. Most autograd bugs look like this.

4.3  The traversal: backward()

Eleven lines, and it is the entire algorithm of §2:

engine.py · Value.backward

def backward(self):

    # topological order all of the children in the graph
    topo = []
    visited = set()
    def build_topo(v):
        if v not in visited:
            visited.add(v)
            for child in v._prev:
                build_topo(child)
            topo.append(v)
    build_topo(self)

    # go one variable at a time and apply the chain rule to get its gradient
    self.grad = 1
    for v in reversed(topo):
        v._backward()

build_topo is a depth-first post-order walk: a node is appended only after all of its children are, so topo runs inputs-first and ends with the node you called .backward() on. Then reversed(topo) walks it root-first. That ordering is the correctness condition of the whole method — a node's _backward may only run once out.grad is final, meaning every consumer of that node has already contributed. Reverse topological order is exactly the order that guarantees it.

self.grad = 1 is the seed: $\partial L/\partial L = 1$. It is also the precise place where "we need the loss to be a scalar" is enforced — you cannot seed a vector with $1$ and this line would be meaningless. That is PyTorch's loss.backward() versus t.backward(gradient=...), and it is §2's $m = 1$ argument reduced to an assignment.

Finally, count the work: visited ensures each node is appended once, and the loop calls each _backward once. One pass, one visit per node — linear in the size of the graph, which is the answer to §5's Q1 sitting in plain sight.

Change one word

Drop the reversed. On a = Value(2.0); b = Value(5.0); L = a*b + a the correct gradients are a.grad == 6.0, b.grad == 2.0; walking topo forwards gives 1.0 and 0.0. Trace why: every node's _backward now runs before its own grad has been set, so it faithfully multiplies the correct local derivative by an upstream gradient of zero. Only the root, which was seeded by hand, does anything at all.

4.4  How a model exposes its parameters

nn.py adds no calculus whatsoever — it is 60 lines of bookkeeping over Value. But it answers a question Handout #3's training loop skipped: when you write optimizer.step(), how does anything know which numbers are the model's?

nn.py · the parameter interface (__repr__ and constructors elided; everything else is verbatim)

class Module:
    def zero_grad(self):
        for p in self.parameters():
            p.grad = 0
    def parameters(self):
        return []

class Neuron(Module):
    def __init__(self, nin, nonlin=True):
        self.w = [Value(random.uniform(-1,1)) for _ in range(nin)]
        self.b = Value(0)
        self.nonlin = nonlin
    def __call__(self, x):
        act = sum((wi*xi for wi,xi in zip(self.w, x)), self.b)
        return act.relu() if self.nonlin else act
    def parameters(self):
        return self.w + [self.b]

class Layer(Module):
    def parameters(self):
        return [p for n in self.neurons for p in n.parameters()]

class MLP(Module):
    def parameters(self):
        return [p for layer in self.layers for p in layer.parameters()]

One contract — parameters() returns a flat list of leaf Values — and it composes by recursion: a layer's parameters are its neurons' concatenated, a network's are its layers'. zero_grad is then a two-line loop defined once, on the base class, and inherited by everything. This is torch.nn.Module in miniature: model.parameters(), the thing you hand to your optimizer, is the same recursive flattening, and PyTorch's version differs mainly in doing the registration automatically (via __setattr__) instead of making you write the list.

Two details worth catching in __call__, both easy to read past. The sum(..., self.b) uses the bias as the start value of the sum, which is how $b$ enters the graph as an ordinary addend rather than a special case. And nonlin exists because MLP.__init__ sets nonlin = i != len(nouts)-1: every layer gets a ReLU except the last. That is not a stylistic choice — a ReLU on the output would clamp every negative prediction to zero and, worse, hand back a zero gradient for all of them.

4.5  Now do something to it

Q1. §1's exercise used $f = \ln x + e^{y} z$. Try to build it with micrograd. What stops you, and what would you have to write?

Answer
Value has __add__, __mul__, __pow__ and relu — and nothing else. There is no log and no exp, so the expression is simply not expressible. Adding them is the best possible exercise on this file, because each is four lines and you cannot fake your way through the local derivative: 
def exp(self):
    out = Value(math.exp(self.data), (self,), 'exp')
    def _backward():
        self.grad += out.data * out.grad      # d/dx e^x = e^x -- reuse out.data
    out._backward = _backward
    return out

def log(self):
    out = Value(math.log(self.data), (self,), 'log')
    def _backward():
        self.grad += (1 / self.data) * out.grad
    out._backward = _backward
    return out
Note the asymmetry that makes the point: exp's local derivative is most cheaply read off the output (out.data), while log's needs the input (self.data). Real frameworks make the same choice op by op, and it is why activations have to be kept around — §2's memory argument, from the other side.

Q2. _prev is a set. What breaks in x * x, and why is it fine anyway?

Answer
_children = (self, other) where both are the same object, so set(_children) has one element and the graph appears to have a single edge where mathematically there are two. It is fine because _prev is used only to decide traversal order, never to count contributions. The two contributions are delivered by the two += statements inside the single _backward closure, which runs once and adds both. Deduplicating the edge is in fact necessary: visiting x twice in the traversal would not double the gradient, but the visited set already prevents that.

Q3. backward() can be called on any Value, not just a loss. What happens if you call it twice on the same node without zeroing, and how does PyTorch differ?

Answer
In micrograd you get double the gradients — the graph is rebuilt and traversed again, and every += lands on top of the values from the first call. (The seed self.grad = 1 is an assignment, so the root itself is not doubled; everything else is.) PyTorch instead raises "Trying to backward through the graph a second time", because it frees the graph after the backward pass — the behavior §3 described. Micrograd keeps the graph alive as long as you hold a reference to the output, which is friendlier to experiment with and much more expensive.

Q4. There is no no_grad in micrograd, and no requires_grad either. What are the consequences at inference time?

Answer
Every forward pass allocates the full graph, unconditionally: a Value object per intermediate scalar, each holding a closure and a set. You cannot turn it off, so evaluating the model costs the same memory as training it. That is exactly the bug §3 warned about — a validation loop without no_grad — except here it is not a bug but the design, which is tolerable only because the graphs are tiny. It also means micrograd has no notion of a constant: inputs and parameters are indistinguishable, and x.grad is computed for the data whether you want it or not.

Q5. How many Value objects does MLP(3, [4, 4, 1]).parameters() return? And roughly how many exist after one forward pass?

Answer
Parameters: $4 \times (3{+}1) + 4 \times (4{+}1) + 1 \times (4{+}1) = 16 + 20 + 5 = \textbf{41}$ — weights plus one bias per neuron, at each of the three layers. Intermediates are far more numerous: every single wi*xi product and every partial sum is its own node, so the first layer alone creates roughly $4 \times (3 + 3 + 1)$ of them. This is the scalar-autograd tax, and it is the one thing PyTorch changes structurally: one tensor node covers a whole matmul, so the graph has a handful of nodes where micrograd would have millions. The algorithm in §4.3 is unchanged — only the granularity is.

5Check yourself

Q1. True or false: backpropagation is a sequential process, and its complexity is a quadratic function of the number of layers. Quiz 1, sp2024 & sp2025

Answer
False — and this is the standard distractor on this topic. It is sequential (you cannot compute layer $k$'s gradient before layer $k+1$'s), but the cost is linear in depth: each node is visited exactly once on the way back. That is the entire point of reverse mode, §2 — if it were quadratic, deep networks would never have become practical.

Q2. True or false: when the gradient flows backward through a sigmoid or tanh nonlinearity, it cannot change sign. Quiz 1, sp2024 & sp2025

Answer
True. The local gradient of a sigmoid is $\sigma(z)\bigl(1-\sigma(z)\bigr)$, which is strictly positive since $\sigma \in (0,1)$; $\tanh' = 1 - \tanh^2$ is likewise positive on $(-1,1)$. Multiplying by a positive number preserves sign. Note the flip side: that local gradient is at most $0.25$ for the sigmoid, so this activation attenuates the upstream signal. The weight matrix can also amplify it; the whole layer need not shrink gradients by four. We study these products in Handout #6. ReLU has local derivative 1 on its positive side (Handout #3 §2.3).

Q3. Why does the backward pass need values computed during the forward pass? Give the smallest example you can.

Answer
Because local gradients often depend on the node's inputs. The smallest example is multiplication: for $h = a \cdot b$, $\partial h/\partial a = b$ and $\partial h/\partial b = a$ — each input's local gradient is the other input's value, so both must be retained. §1's $\partial h_3/\partial z = h_2$ is exactly this. The consequence is the memory cost in §2: activations are kept alive from forward to backward, which is usually what limits batch size.

Q4. You evaluate your model on a validation set inside the training loop and run out of GPU memory, even though the validation set is smaller than a training batch. What did you forget, and why does it matter so much?

Answer
Check whether validation uses torch.no_grad(). Recording an unneeded graph increases memory for a forward pass; retaining graph-connected outputs or losses across batches can keep multiple graphs alive. Graphs do not automatically accumulate if no references remain. model.eval() changes dropout and batch-normalization behavior but does not disable graph recording. Actual memory limits depend on parameters, optimizer state, activations, and temporary storage.
